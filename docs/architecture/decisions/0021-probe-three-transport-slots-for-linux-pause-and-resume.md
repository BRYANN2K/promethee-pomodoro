# ADR-0021: Probe three transport slots for Linux Pause and Resume

## Context and problem

ADR-0020 made Linux x64 a passive target. It discovers Promethee's process and windows, attaches the companion's surfaces to the real HUD, and stops there: `supportsNativeAutomation` returns false, so none of ADR-0011's or ADR-0016's Pause and Resume authority reaches it.

Automation needs exactly two things the Linux target does not have. It needs a bounded capture of the already validated HUD rectangle, twice, the second immediately before dispatch. It needs one left-click pair at a point the Electron controller derived from that capture. Everything else in the path, the two SQLite reads, the identity and generation binding, the single dispatch, the absence of retry, the indeterminate receipt, is platform-independent and already written.

On macOS those two things are one CLI and one API that work on every session. `/usr/sbin/screencapture` captures any rectangle and CoreGraphics posts the click. Linux has no equivalent pair. A Wayland client cannot read the screen or move the pointer through any protocol that all compositors implement, and which mechanism is available depends on the session rather than on the distribution. The XDG portals are the sanctioned answer and do not cover the compositor this work was measured on: the Hyprland portal implements ScreenCast and does not implement RemoteDesktop. The wlroots protocols cover Hyprland, Sway, river and Wayfire and are absent on GNOME and KDE. X11 covers neither of the above and still covers a real population of sessions.

So the question this decision answers is not whether Linux can be automated. It is which mechanism gets asked, in what order, and what the app is allowed to claim when the answer is no.

## Scope and non-goals

This decision covers the Linux capture transport, the Linux injection transport, what `permission-status` means on Linux, the consent the user is asked for, and the compositors that are refused. It does not change the action preflight, the set of allowed actions, the acknowledgement limits, or the no-retry rule, all of which stay exactly as ADR-0011 and ADR-0016 left them. It authorizes no Start, Stop, End, task mutation, database write, private IPC, broad screenshot, OCR, arbitrary coordinate, or global shortcut. It does not put Linux into the release, tarball or smoke matrices: ADR-0020's exclusion stands until Linux has the evidence that decision asks for.

## Decision

Linux SHALL be eligible for the same action authority as macOS and no more: exactly `session.pause` and `session.resume`, behind every gate already in force. What follows is only how the capture and the click happen there.

### Three slots, fixed order, no fall-through

Capture and injection SHALL each be a probe across three slots, tried in a fixed order, first that binds wins.

Capture:

| Slot | Protocol | Sessions |
|---|---|---|
| 1 | `ext-image-copy-capture-v1`, sourced from an `ext-foreign-toplevel-list-v1` handle | Hyprland, Sway, river, Wayfire |
| 2 | portal ScreenCast over PipeWire | GNOME, KDE |
| 3 | `XCompositeNameWindowPixmap`, then `XGetImage` on that pixmap | X11 |

Injection:

| Slot | Protocol | Sessions |
|---|---|---|
| 1 | `zwlr_virtual_pointer_v1` | Hyprland, Sway, river, Wayfire |
| 2 | portal RemoteDesktop with libei | GNOME, KDE |
| 3 | XTEST on `$DISPLAY` | X11 |

wlroots is asked first because it is the only injection slot that covers the session this work was measured on, and because the portal that would otherwise serve that session does not exist there.

Slot 2 is declared here and deliberately not built. The probe keeps its place in both orders, so a session that would answer through the portal is asked in the right sequence the day the slot exists, but this work ships slots 1 and 3 and stops. That is a scope decision and not a technical finding: the two desktops slot 2 serves, GNOME and KDE, are out of scope for this round, and building the largest dependency in the project for desktops nobody is asking this to run on would be work with no session to check it against. Until it is built those two desktops get `automation-unsupported`, which is the honest answer for a session this helper has no mechanism to reach, and the measurements below say the same thing from the other direction.

The two tables no longer line up, and the reason is worth stating because the first draft of this decision had them lining up exactly. It named `zwlr_screencopy_v1` for capture slot 1, and `zwlr_screencopy_v1` cannot do this job at all: it copies an output or a rectangle of one, and the translucent-HUD measurement below says a rectangle of the screen is not something the classifier can read. What replaces it is not a wlroots protocol and not a compositor's own. `ext-image-copy-capture-v1` is a sanctioned staging protocol, and asked for a source from `ext_foreign_toplevel_image_capture_source_manager_v1` it copies one toplevel's surface, alpha intact and nothing of the desktop in it. That is the raster the classifier was written for, on a protocol no single compositor owns. The first version of this paragraph went one step further and claimed the slot reached KDE as well as wlroots, which was inference from the protocol being sanctioned rather than a measurement, and the measurement below says otherwise. The two tables are now unaligned on both sides of KDE, not just one.

Capture slot 3 was corrected for the same reason and in the same direction. It said `XGetImage` on `$DISPLAY`, which is the X11 spelling of the mistake `zwlr_screencopy_v1` was: X11 will hand any client a rectangle of the root window, and a rectangle of the root window is a translucent HUD blended with the desktop behind it. `XCompositeNameWindowPixmap` names the window's own off-screen contents and `XGetImage` reads that instead, which is the same picture slot 1 asks its compositor for. The slot therefore requires the Composite extension at version 0.2 or later, and a server without it is a slot that is absent rather than one that failed.

Capture SHALL be probed on every session, including the ones automation is refused on. It reads and never acts, so a compositor this project has no action evidence for can still be told the truth about what it offers.

Which slot answers SHALL follow the window server that answered `windows`, and SHALL NOT be chosen independently of it. A Wayland session runs an X server too, so both mechanisms are usually reachable at once, and they do not describe the same windows: a native Wayland toplevel is not in the X11 tree at all. Reading pixels through one and coordinates through the other would be two answers about two different things, which is the same failure the no-fall-through rule exists to prevent, reached by a different route.

A slot that is present and then fails SHALL NOT fall through to the next. This is the rule ADR-0020 already set for window discovery and it holds here for the same reason: the next slot answers for a different display, so falling through would capture a screen or click a point belonging to another session. A failed slot is a typed failure and automation stays unavailable.

The two probes are independent. A session that can capture and cannot inject is a real and expected configuration, and it SHALL report itself that way rather than resolving to all or nothing.

### What permission means where the system grants nothing

`permission-status` on Linux SHALL keep the frozen wire format, `permissions,<inputEvents>,<screenCapture>`, and SHALL report what the probes actually found. `screenCapture` is 1 only when a capture slot bound, and `inputEvents` is 1 only when an injection slot bound.

That is a weaker standard than the macOS probe, which takes a real one-pixel capture and decodes it, and the difference is not laziness. macOS asks a recorded grant whether a future call will be allowed, and a recorded grant is a claim rather than the call, so the only way to know is to make the call. Binding an `ext-image-copy-capture-v1` manager is the call: it is the same act the helper performs to take a frame, and there is no separate permission behind it that could answer differently a moment later. What binding does not prove is that a frame will arrive, and the app SHALL treat a capture that binds and then fails as a typed failure at use time rather than as a permission it should have caught earlier. The Electron side accordingly SHALL NOT run a second capture probe on Linux, because a second probe would repeat the first and report the same thing.

That format carries two answers and Linux needs three. macOS only ever has two, because its mechanism is always present and always has an opinion, so every outcome is a grant or a refusal. On Linux a slot can simply not be in the session, and calling that a refusal would send the user to look for a setting to turn on that does not exist anywhere on their machine. So a session in which no slot of a kind is present SHALL answer under its own receipt, `automation-unsupported`, and the app SHALL read it as the feature being unavailable here rather than denied here. The two bits keep their meaning for the case they were made for, a mechanism that is present and said no, which is what the portal slot will do and what the wlroots slot never can.

The same reading SHALL extend to every answer the app could not read at all, on Linux and not on macOS. An unparseable receipt or a helper that will not run says nothing about whether a mechanism exists; assuming one exists and refused is a claim, and it is the claim that puts a recovery prompt in front of a session with nothing to recover. Where the mechanism is not assured, silence SHALL leave the feature unavailable, and only the probe itself SHALL be able to report a refusal.

`supportsNativeAutomation` SHALL accordingly stop being the thing that decides whether Linux can act. It returns true for Linux, meaning this build carries a helper that can press a control, and the probe decides the rest. Nothing arms on that return value alone.

A passing probe is necessary and not sufficient. Linux SHALL also require the explicit in-app consent ADR-0011 requires, Pause and Resume SHALL remain separate settings, and `PROMETHEE_POMODORO_DISABLE_AUTOMATION=1` SHALL override both here as everywhere.

That separation matters more on Linux than on macOS, and the consent copy SHALL say why rather than leave it implied. On the wlroots slot the virtual-pointer protocol is unprivileged: any client that can open the Wayland display may move the seat pointer, with no prompt, no grant, and nothing in system settings to revoke. A user who reads "Input Events" and expects a system toggle to fall back on does not have one on that slot. The in-app setting is the whole of the consent that exists there, so it is the thing that has to be honest. The portal slot behaves the opposite way and prompts per session, which is a different user experience for the same feature and SHALL be described as such rather than smoothed over.

The consent copy SHALL also say that the cursor does not come back. macOS reads the pointer position before it moves it and puts it back afterwards, so a Pause the user did not watch leaves no trace on screen. Wayland gives a client no way to ask where the pointer is, so on that slot there is nothing to restore it to and the cursor is left parked on the control it pressed. That is the automation moving something the user is holding, which is a different thing from it pressing a button, and it is not the kind of surprise a setting should spring after the fact.

X11 is the exception and SHALL behave as though it were not. `XQueryPointer` reads the cursor, so slot 3 could restore it, and it does not. The copy is chosen per platform rather than per slot, so a slot that behaved better would be a slot behaving differently from what the user was told, and the user cannot tell which slot they are on. Uniformity is the weaker behaviour here and the honest one, and the trigger for changing it is stated below.

### i3 stays passive, Sway no longer does

Automation SHALL be available on Sway on the same terms as on Hyprland. It SHALL remain unavailable on i3, and `permission-status` SHALL report `inputEvents` as 0 there.

This section has narrowed three times and this is the last of them, so the whole path is kept rather than replaced. The original reason to refuse Sway was that it has no per-window way to take a box out of the running for the pointer, so the companion's own outline sat on the real pill and an injected click would have landed on the outline rather than on Promethee. That stopped being true when the outline started being refused and taken down for the session on such a compositor, which uncovers the pill. The reason then became that a real Sway had never run any of this. That stopped being true when a nested Sway 1.12 ran the window backend and answered with the geometry of a window that was really there, checked against a bogus socket that answered `window-list-incomplete` instead. What was left was that no press had ever been sent there and no capture had ever succeeded there, the second because that session offered the toplevel only in a format this helper refused. The refusal was written to be lifted by a capture and a press on a real Sway rather than by a protocol change.

Both have now happened, on a real Sway 1.12. `capture` returned `captured,159,32,0` and wrote a raster this project could check against a fill it computed independently, with no pixel off by more than one and every alpha byte at 255. `permission-status` returned `permissions,1,1`. A Pause press returned `clicked-unconfirmed,pause,0` and the target client reported a left button press and release arriving on its own surface at `108,16`, which is the planned point `191,551` minus the window origin `83,535`. A Resume press landed at `76,16` the same way. A rectangle moved by one pixel was still refused with `timer-not-found` and sent nothing.

i3 keeps the refusal, and the two are told apart without asking the compositor what it is: Sway sets both `SWAYSOCK` and `I3SOCK`, i3 sets only its own. i3 is X11. It has no wlroots pointer to bind and depends on the X11 slot, and that slot has since been built and exercised, so the ground for the refusal has narrowed to the one thing the Sway refusal was lifted by and this one is not: no i3 session has run any of it. Capture is a different matter and i3 gets it, through the same X11 slot and by the rule above that reading is not acting. Building the slot therefore changed what i3 is offered without changing what it is allowed to do, which is the intended shape of that split rather than an oversight in it.

### The classifier is not ready and gates everything above

The shipped `classifyPrometheeHudRaster` SHALL NOT be applied unchanged to a Linux HUD, because it rejects it. Until it accepts a Linux HUD in both states, Linux automation stays unavailable no matter what the two probes report. A transport that works feeding a classifier that says `unsupported` is not automation, and shipping the transports without this would produce a feature that is enabled and never fires.

The classifier SHALL place the control it is about to click on what the raster shows rather than on the offset that found it. The offsets stay: they say where to look, and looking in the wrong place is not the failure. The failure is clicking where the offset says instead of where the control is.

The centre is taken from the Pause glyph itself, because two equal bars either side of an empty gap have an unambiguous midpoint, and that midpoint is the control. Reading the disc instead was tried and does not work. A disc does read as a run of constant ring value, but the run is bounded by the glyph inside it and not by the disc edge, so its midpoint is the glyph's midpoint and only agrees with the control when the glyph is symmetric. The Play triangle is not, and locking to that run moves the paused controls a pixel. Measuring the Pause bars has no such dependency and touches only the one control this decides to click.

The paused controls keep their offsets, and a capture now says they are right: on a 191-wide paused HUD all three land inside their disc. What did not survive contact with that capture is the Play glyph test, and the correction is the same in kind as the Pause one. A glyph SHALL be judged by proportions of its own bounding box rather than by pixel counts in buckets pinned at a fixed distance from the control centre. Promethee draws the same triangle six columns wide on Linux and ten in the fixture, and a bucket boundary that separates the flat edge from the point at one size cuts through the middle of the glyph at the other.

The classifier SHALL NOT be given a raster in which anything behind the HUD is visible. Promethee's HUD is translucent, so a capture of the screen region it occupies carries whatever is under it, and the classifier's flatness gates cannot survive that: over a dark empty desktop a control ring reads a range of 0.0353 against a limit of 0.05, and over ordinary application content the same ring reads 0.1778 and 0.4588. The margin is 0.0147 in the good case and there is no threshold that both admits a contaminated disc and still rejects a non-disc. This is a requirement on the capture slot, not on the classifier: the transport SHALL deliver the HUD surface itself.

A surface is not yet a raster the classifier accepts, because the surface is translucent and the classifier reads no pixel with an alpha below 230. So the transport SHALL composite it before handing it over, and SHALL composite it over opaque black. Black is not a default here, it is the answer. Wayland's shm buffers are premultiplied, so over black the stored value is already the composited value and there is no arithmetic that can be got wrong. It is also the one background that is identical on every session, which is what makes a classification reproducible: the same HUD read twice gives the same pixels whatever the user's wallpaper is doing. It is not merely convenient either. The running discriminator wants `baseMean - optional.mean >= 0.10`, and that difference shrinks as the background brightens: the same measured surface classifies `running` composited over 0, 32 and 64, and `unsupported` over 128.

The classifier's fixtures SHALL stop being drawn from the constants under test. A fixture painted at exactly the offsets the classifier samples cannot fail when those offsets are wrong, which is why this was found by a capture and not by the suite. At least one fixture SHALL place its discs on a half pixel, as a real HUD does.

## Platform and evidence boundary

### What the live session actually is

Every live measurement in this decision and in ADR-0020 was taken on one machine, and no compatibility layer is involved anywhere in it. The session is Arch Linux, kernel 7.0.5-arch1-1, on Hyprland 0.55.0 built from branch `v0.55.0` at commit `af923e30d1d24f1f4a4f5cb8308065173c1d9539`. The companion is this repository, built by its own `target:build` and started by `target:start`, on Node 26.4.0 and Electron 43.2.0, which is the version the lock file pins for macOS and Windows as well.

Promethee itself needs the longer answer, because it publishes no Linux build, so what runs here is neither an official Linux release nor a Windows one under emulation. It is Promethee 1.3.26, and the payload is Promethee's own Windows release: a separate project fetches the current Squirrel `.nupkg` from Promethee's release channel, verifies it against that channel's `RELEASES` manifest, extracts `app.asar`, and runs the extracted application on a Linux Electron 43.2.0. Nothing Windows-native survives that trip. The built tree carries no `.exe`, no `.dll` and no prebuilt `.node`, the running process has no Wine, Proton, Bottles or CrossOver variable in its environment and maps no such library, and the compositor lists both Promethee toplevels with `xwayland: false`, so they are Wayland surfaces rather than X clients being translated. Each of those was read off the live process rather than assumed.

Four JavaScript patches are applied on top, and they are this project's rather than Promethee's, so it is worth saying what they touch. All four are main-process shims: an active-window backend for a platform upstream's dispatcher returns null on, overlay window handling for the properties Wayland makes no-ops, durable writes for the three session files, and a control socket over the existing `ipcMain` handlers. None of them touches the renderer, so the HUD the classifier reads is upstream's own drawing, unmodified. One of them names Promethee's windows per role, which is convenient for reading a measurement and is deliberately not load-bearing: the helper matches Promethee on the class the window server reports and never on a window title, and it tells the HUD from the main window by the geometry the caller named, both of which upstream sets.

The qualification that leaves is real and belongs on every row of evidence below. What has been measured is upstream's renderer, on an official Linux Electron, under a patched main process. What has not been measured is a Promethee that Promethee shipped for Linux, because there is not one.

### The drag half of the pointer test, and what it did not settle

ADR-0020 records the click leg of the pointer test exactly: the real Pause button's own rendered hover state, captured with the outline's `no_focus` property set and again with it cleared, in both orders, on the Hyprland build named above. The review asked for the drag leg beside it, on the ground that `no_focus` names focus rather than pointer delivery, so a click passing through is not by itself proof that a press-and-move does. That leg was attempted on 2026-08-27, it did not settle the question, and it is recorded here as an attempt rather than as a result.

The method was the virtual pointer the click leg used. Press the left button over the pill at a point clear of both controls, walk twelve interpolated steps across 200 pixels at 30 ms a step, release, and read the HUD's rectangle from `hyprctl clients` before, during and after. With the outline covering the pill the pointer walked the whole path and the HUD did not move. The control leg was the identical drag with the companion shut down and nothing at all over the pill, and it did not move the HUD either, nor did three further grab points spread across the pill's width.

A drag that moves nothing with the outline and nothing without it separates nothing. It is equally consistent with the outline swallowing the drag and with this HUD not being movable by a pointer drag in the first place, and nothing in the measurement chooses between them. That the virtual pointer reaches the HUD is not what is in doubt: the same pointer on the same session pressed the real Pause and the real Resume, and the HUD changed geometry both ways. What is in doubt is only whether a press-and-move is a gesture this window answers, and until that is established independently the drag cannot serve as a passthrough probe at all. The click leg therefore stays the whole of the pointer evidence, and this project claims no more than that leg proves: on this compositor, with that property set, a click reaches the pill through the outline, and without it the click stops at the outline.

There is one further reason the attempt was stopped rather than repeated. The session under test is the owner's working desktop. Partway through, the pointer moved with no injection in flight and the HUD's position changed between commands, which is precisely the effect a synthetic drag was meant to be the only possible cause of. A measurement of this shape wants a session nobody else is touching, and running it on one that somebody is contaminates the control leg more than it proves anything about the outline.

### The injection slot

The injection slot is the only part of this decision with live evidence, and it was measured for a different purpose. On Hyprland 0.55.0, commit `af923e30d1d24f1f4a4f5cb8308065173c1d9539`, `zwlr_virtual_pointer_v1` positioned the seat pointer pixel-exactly, unprivileged, with no prompt, and the target HUD rendered the hover state that proves the event was delivered to it. Output-local translation has to come from `zxdg_output_v1` logical position, because Hyprland reports `wl_output.geometry` as 0,0 for every output; with that translation the position was correct across outputs. That is recorded in ADR-0020 and is the whole of it.

That slot is now built into the shipped helper rather than measured beside it, and the built version was exercised on the same session. The helper's `click` carries the macOS contract argument for argument, and every refusal in it was driven with a live Promethee running: a short argument list, an action that is not Pause or Resume, an action that disagrees with the state, a non-numeric field, a HUD height that is not 32, a control count that disagrees with the state, a target one pixel off the offset the width implies, a process id that is not the one on screen, and a window rectangle that has moved. Each answered with the receipt macOS answers with, and none of them reached the pointer. `SWAYSOCK` set turned the same call into `permission-denied` and the probe into `automation-unsupported`, which is the compositor refusal below, working.

The pointer path itself was then run through the shipped code with the two `button` calls suppressed in a scratch copy, on a live 159x32 HUD at 1189,366. It computed the Pause target as 1297,382, re-verified the process and the rectangle against the compositor, chose the output whose logical rectangle contained the point, and moved the seat pointer there: `hyprctl cursorpos` read 983,540 before and exactly 1297,382 after. Everything but the press was therefore exercised in the code that ships before any action had been sent.

The press has since been sent, once in each direction, with the owner of the session authorizing each one. On 2026-08-27, against a live Promethee on the same Hyprland session, the shipped helper answered `clicked-unconfirmed,pause,0` and the HUD moved from 159x32 at 1189,366 to 191x32 at 1173,366, which is the paused geometry ADR-0016 recorded on macOS. The capture slot then read that paused surface and the unmodified classifier called it `paused` with three controls. The Resume that followed answered `clicked-unconfirmed,resume,0` and the HUD returned to 159x32 at 1189,366. Both targets were computed by the classifier and the planner from the captured raster, 1297,382 for Pause and 1281,382 for Resume, and both were recomputed by the helper from the geometry alone before it would act. The receipt is still `sent-unconfirmed` in both directions: the helper reports that it moved the pointer and pressed, never that Promethee acted, and the geometry change is this project's observation rather than the helper's acknowledgement.

Capture slot 1 is now built and measured on the same session, and it answers the question the first draft of this decision left open rather than working around it. Live Hyprland 0.55.0 advertises all three of `ext_image_copy_capture_manager_v1`, `ext_foreign_toplevel_image_capture_source_manager_v1` and `ext_foreign_toplevel_list_v1`. Against a running 159x32 HUD at 1189,366 the shipped helper's `capture` answered `captured,159,32,0` and wrote 20352 bytes, and the unmodified `classifyPrometheeHudRaster` read that file as `running` with controls at x 94 and x 126. Those are the same two controls the injection path independently computed: 1189 plus 108 is 1297, the Pause target the pointer was driven to with the press suppressed. The two halves agree without having been made to.

That the buffer holds the surface and not the screen was checked rather than assumed. The HUD's corner pixel comes back fully transparent black, and both control rings read a range of 0.0000 at every background the capture was composited over, against the 0.0353 the same rings read on a screen region over an empty desktop. There is nothing of the desktop in it.

Separating the HUD from Promethee's main window needed one thing the protocol does not offer directly. `ext_foreign_toplevel_handle_v1` reports an `app_id` and no geometry, and both Promethee toplevels carry the same `app_id`, which is the same identity the window backend already matches on and the only identity this helper is willing to match on. So the helper opens one capture session per candidate, reads the buffer size the compositor would fill, and keeps the one that matches the geometry the caller named: no match is `timer-not-found`, more than one is `timer-ambiguous`. That also refuses a fractional-scale output for free, where the device-pixel buffer would not equal the logical rectangle the caller measured.

The refusal paths were driven live and none of them wrote a file: a short argument list, a non-numeric field, a height that is not 32, a width below and above the classifier's range, an empty output path, a process id that is not the one on screen, a window rectangle that has moved, and an output path that cannot be opened. A session with no Wayland display answers `capture-unsupported`, which is the one refusal here that means the slot is absent rather than the request wrong. The Electron side was then run end to end on the live HUD, from `captureLinuxPrometheeHud` through the classifier, so the seam between the helper's file and the classifier's raster is exercised and not argued.

Capture on a compositor whose automation is refused was checked too. With `SWAYSOCK` set, `capture` still succeeds and `permission-status` still answers `automation-unsupported`, which is the split this decision asks for: reading is offered where acting is not.

Capture had no evidence for the paused state for as long as the press had none, since taking a paused surface means pausing a real session. Both arrived together on 2026-08-27. The slot captured the 191x32 paused HUD the authorized Pause produced, and the unmodified classifier read it as `paused` with all three controls at the offsets recorded above, from the surface rather than from the screen. The paused rasters the classifier was originally measured against came from screen-region captures, and this slot now agrees with them.

Four other sessions have now been measured, each nested inside the live one so that none of it is inference. The method is the same every time: start the compositor on its own socket, ask a plain client for the global list, then run the shipped helper against it and record what it answers.

| Session | Capture slot 1 protocols | `zwlr_virtual_pointer_manager_v1` | `windows` | `permission-status` |
|---|---|---|---|---|
| Hyprland 0.55.0, live | present, offers ARGB8888 | present | real geometry | `permissions,1,1` |
| Sway 1.12, nested | present, offers only `BG24` | present | real geometry | `permissions,1,1` |
| KWin 6.6.5, nested | absent | absent | `process-not-found` | `automation-unsupported` |
| Mutter 50.4, headless | absent | absent | `window-list-incomplete` | `automation-unsupported` |
| Xorg 21.1.24, nested | not applicable, slot 3 instead | not applicable, XTest instead | real geometry | `permissions,1,1` |

Sway is the result this decision did not expect. It advertises every protocol both halves bind, so the automation refused there was refused by this project's choice and not by the session's inability, and this record SHALL stop implying otherwise. What it did not offer is a format: `ext-image-copy-capture-v1` on that session lists exactly one shm format for a toplevel, `BG24`, and this helper asked for ARGB8888 by name because dropping the alpha would throw away what makes the HUD readable. Both a synthetic client committing an ARGB8888 buffer and a GPU-rendered terminal got the same single offer, so it is the session's answer and not one client's.

That refusal came back as `timer-not-found`, which was wrong and is now fixed. The toplevel was listed, its size matched the rectangle the caller named, and only the format did not. `timer-not-found` says the HUD is not on screen, which sends a reader to measure the geometry again; the truth was a session this slot cannot serve. The helper gains `capture-format-unsupported`, exit 3, alongside `capture-unsupported`, and the app SHALL read it the same way: unavailable, not a wrong request.

### The format demand was the wrong half of the argument

Capture SHALL accept ARGB8888, XRGB8888 and BGR888, in that order of preference, and SHALL keep producing the same over-black RGBA raster from all three.

Asking for ARGB8888 by name was a reasonable-sounding rule that turned out to be a reach limit, and the way it was found is the point. The single `BG24` offer looked like Sway's answer, so the next question was whether it was a consequence of nesting inside another compositor. It is neither. A Sway with its own headless backend, drawing into no parent buffer at all, still offers `BG24`. The same Sway started with `WLR_RENDERER=pixman` offers XRGB8888 instead. The offered format is the renderer's answer, so demanding ARGB8888 by name did not protect the alpha on a slot that four compositors share, it locked the slot to the one compositor that happened to offer it.

The alpha it was demanded for is not needed, and that is a measurement rather than an argument. This helper writes the surface composited over opaque black, on purpose and for reasons stated above. A Wayland shm buffer is premultiplied, so the colour channels of a copy that dropped the alpha are already that same composite. Tested where both formats exist: the same live 159 by 32 Promethee HUD on Hyprland, captured once as ARGB8888 and once as XRGB8888, differed in none of its 15264 colour bytes. The classifier reads the same raster it always did, and needs no recalibration.

BGR888 is the one that changes the packing rather than just the fourth byte: three bytes per pixel, red first. It was checked against a client whose fill this project computes rather than against another capture, because a channel swap survives comparing two captures of the same thing and does not survive that. Not one of 5088 pixels was off by more than one, and every alpha byte came out at 255.

Hyprland still answers `captured,159,32,0` for the same live HUD after the change, and the raster it produces is byte-identical to the raw ARGB8888 frame the compositor handed over. `capture-format-unsupported` stays, and now names a session offering something none of the measured ones offered rather than the common case.

Mutter is worth one sentence beyond its row. It offers no window-listing protocol at all, so on GNOME the discovery ADR-0020 built has nothing to bind either, and `windows` answers `window-list-incomplete`. GNOME therefore gets neither automation nor the attached surface, which is a wider gap than the injection tables alone suggest.

The X11 row was falsified rather than just observed. A client with the matching class in a nested Xorg was read as `0,0,159,32`, which was close enough to a HUD's size to be worth doubting, so the client was restarted at 300x100 and the helper answered `0,0,300,100`. It is reading the server, not repeating a constant.

### The X11 slot is built, and it does not read the screen

Both halves of slot 3 SHALL exist and SHALL be reached through the rule above rather than as a fallback: capture through the window's own Composite pixmap, injection through XTest.

The capture half is the interesting one, because X11 makes the wrong thing easy. Any client may read any rectangle of the root window, with no extension and no permission, and that is precisely the picture this decision has already refused once: over a real desktop a translucent HUD read off the root carries whatever is behind it, and the classifier's flatness gates cannot tell such a raster from a valid one. `XCompositeNameWindowPixmap` gives the window's own contents instead. It answers only for a window somebody has redirected, and on any session where the HUD looks translucent at all a compositing manager is running and has redirected everything, so naming the pixmap is normally the whole of it. Where nothing has, the helper redirects the window itself and undoes it afterwards, and that fallback is the weaker of the two paths: a window redirected a moment ago holds only what it has repainted since, so the picture depends on the client answering an exposure in time.

The colour masks come from the window's visual and not from the returned image, which is not a preference either. A pixmap has a depth and no visual, so the server answers `GetImage` on one with no visual id at all and Xlib hands back an image whose red, green and blue masks are every one of them zero. Read from the image, every X11 capture would have been refused as an unreadable packing; read from the window, the packing is the one the client actually drew in. This was found by the slot refusing its first capture, not by reasoning about it.

The evidence is a nested Xorg 21.1.24 and a synthetic client, and it is the same standard the Sway evidence was held to. The client carries the matching class and a `_NET_WM_PID`, renders through a 32-bit ARGB visual, and draws a premultiplied fill this project computes independently, so a capture can be checked against what it should be rather than against another capture. Both capture paths were exercised, once with a stand-in that redirects every top-level window the way a compositing manager does, and once on a bare server where the helper had to redirect the window itself. Each returned all 5088 pixels within one of the computed fill, with every alpha byte at 255.

The falsification is the part that distinguishes this slot from the one it refused to be. An opaque magenta window the same size as the HUD was raised over it, so that the HUD was completely covered. A root grab of that rectangle came back 5088 magenta pixels and nothing else. The helper's capture of the same rectangle at the same moment came back byte-identical to the capture taken with nothing covering it. The two reads are demonstrably not the same read.

The refusals behave as they do on the other slots. A rectangle one pixel stale answered `timer-not-found` and wrote no file. A target past the screen edge, from a HUD placed at 1200,700 on a 1280x720 root, answered `target-mismatch` and sent nothing.

The injection half is XTest, which is old, unprivileged and on every X server anyone runs. `permission-status` on that session answers `permissions,1,1`, where the same nested Xorg used to answer `automation-unsupported`. A Pause press returned `clicked-unconfirmed,pause,0` and the target client reported a left button press and release arriving on its own surface at `108,16`, the planned point `208,96` minus the window origin `100,80`. A Resume press landed at `76,16` the same way. Those are the same two window-local points the Sway exercise produced, which is what a slot-independent planner is supposed to produce.

One thing X11 could do better and does not. `XQueryPointer` reads the cursor position, so this slot could put the pointer back where it found it, which is what the macOS helper does and what the Wayland slot cannot. It does not, because the consent copy the user has already read says the automation leaves the pointer on the control it pressed, and one sentence that is true of every Linux session is worth more than a slot that quietly behaves better than its own copy. Changing that means changing the copy first, and the copy is selected per platform rather than per slot.

What this slot still lacks is what the Sway evidence lacks: no real Promethee has been captured or pressed through it, and every session it has run on was nested. It has never run under a real compositing manager either, only under a stand-in that redirects and draws nothing.

The first of these measurements moved KDE out of capture slot 1. A nested `kwin_wayland` 6.6.5 on its own socket advertises 64 globals to a plain client and none of them are `ext_image_copy_capture_manager_v1`, `ext_foreign_toplevel_list_v1` or `zwlr_virtual_pointer_v1`. It does advertise `wp_security_context_manager_v1`, `ext_data_control_manager_v1`, `zwlr_layer_shell_v1` and `wp_pointer_warp_v1`, so the list is a real list and not a stripped one. KWin routes screen capture through xdg-desktop-portal, which is slot 2, and it is slot 2 on the injection side already. The shipped helper run against that session answers `ready,1,pause-resume` for `self-test`, which is about the build, and `automation-unsupported` for `permission-status`, which is about the session and is the correct fail-closed answer for a session where both slots are absent. This is a nested compositor and not a KDE login, so it is evidence about what KWin 6.6.5 offers a client and not about a full Plasma desktop, where the portal is running and would answer for slot 2 if slot 2 existed.

Nothing else here is proven. There is no evidence for either half of slot 2, none for either portal on any session, and so none for GNOME or KDE at all. Every session above except Hyprland was nested inside it, which measures what a compositor offers a client and not what a full desktop login does. Only Hyprland has captured or pressed a real Promethee; Sway and X11 have answered every command against a synthetic client and nothing else.

Two smaller things follow from the helper gaining both halves. Its `self-test` receipt is `ready,1,pause-resume`, the same receipt macOS carries, which is what a build with a working capture and a working press has to say. That receipt is about this build and not about the session it runs in, which is why it reads the same on a CI runner with no compositor at all, where `permission-status` says `automation-unsupported` in the same breath. And a click needs one receipt macOS has no use for: the window server this helper reads geometry from can fail to answer, which is not the same as finding no window, and the app SHALL read `window-list-incomplete` as a click that provably did not happen rather than as an unreadable receipt that leaves a reconciliation pending.

The classifier gap was measured rather than assumed, on a 145x32 running Linux HUD, maxX 144. Sweeping the classifier's own ring probe across every column of that raster shows what the probe can and cannot do. It holds steady at mean 0.2296 over two plateaus, x 91 to 98 and x 122 to 130, which are the two control discs, against a background that reads 0.0922. So the ring finds the discs. It cannot find their centres: the reading is identical at every column inside a plateau, because a disc's interior is uniform, so any centre inside one satisfies the gate equally. The two hardcoded offsets, `maxX-50` at 94 and `maxX-18` at 126, both land inside their plateau, which is why the ring gates pass and report nothing useful.

The gate that does the work then fails. The Pause glyph test at 94 finds 7 bright pixels in the column its gap bucket allows at most 1 in. Centred on the bars themselves it reads 24 pixels left, 0 in the gap, 24 right, which is as clean as that test can come out. The bars sit at 92, 93, 96 and 97, so their midpoint is 94.5 and the offset is half a pixel left of it. The whole failure is that half pixel, and measuring the bars removes it. Only the reading moves. The control does not: sweeping row 16 puts the disc at 81 to 108, and the target stays at 80 to 107 on the offset, because both native helpers recompute that same offset from the window they are pressing and refuse a `click` that names anything else. A target measured from the raster and a target recomputed from the window are two answers to the same question, and the one the helper will accept is the offset. So the measurement is used to decide that this is a Pause, and never to decide where to press.

That shape is what keeps the change additive. The existing test is asked first and left exactly as it was, the measured one is asked only when it says no, and no raster that used to classify stops classifying.

The other gate passes for the wrong reason rather than failing. The running and paused discriminator requires `baseMean - optional.mean >= 0.10` and clears at 0.1079, a margin of 0.0079, at offset `maxX-82`, which is 62 here and lands inside the timer text rather than on a third disc. It is reading digits and getting the right answer.

The paused state was then captured too, from the same session paused by hand: 191x32, maxX 190. There the three offsets are exactly right. All three rings land inside a disc and read a range of 0.0000, and `maxX-82` finds a real third control rather than the timer digits it was reading at 145 wide. The refusal moves to the Play glyph test, and to one clause of it. The triangle is found, 31 pixels, 6 columns wide and 7 rows tall, its mass a little above centre, all of which the test accepts. What it rejects is the balance: the clause asks for at least 1.4 times as many pixels at least two columns left of the control centre as at least two columns right of it, and gets 6 against 6.

The cause is that the fixture triangle is ten columns wide and this one is six. At ten wide the left bucket holds three columns of the flat edge and the right bucket four columns of the tapering point, so the ratio means something. At six wide the left bucket holds one column and the right bucket two, and a correct triangle fails. Measuring the halves against the glyph's own bounding box instead of against fixed offsets gives 19 against 12 on the same pixels, and the capture classifies `paused` with controls at 94, 126 and 158, which is where sweeping row 16 says the three discs are.

That is the second time the same mistake has shown up in this classifier: a constant that describes one rendering of one glyph on one platform, applied as though it described the shape. The Pause offset was the first.

Both are answered the same way, and the way is chosen for what it does to macOS rather than for what it does to Linux. Neither existing test is edited. Each is asked first and, only where it says no, a second test is asked that measures the glyph against its own bounding box. Both conditions therefore only ever widen what classifies, so no raster that classified before this change stops classifying, and macOS keeps every reading it had. The cost is that the pixels are gathered twice on a HUD that needs the second test, which is a fifteen by thirteen window read at the cadence of one Pause or Resume.

One more thing about the evidence, which is about macOS rather than Linux. The classifier's fixtures are drawn by the test suite at exactly the offsets the classifier reads, with discs centred on whole pixels and glyphs painted symmetrically around those same centres. They are generated from the constants under test, so they move whenever those constants move and cannot disagree with them. That is why a half-pixel error survived to be found by a capture from a different platform, and it means the suite currently offers no protection against changing these offsets. The recorded live macOS paused HUD is 191 wide and the paused fixture is 173, so the fixtures do not match the one live measurement the project has either.

Two actions have now been sent to a live Promethee process on Linux, and this record earlier said none had, which was written before the run and left standing after it. Each was authorized on its own by the owner of that session, which is what ADR-0011 requires per platform and what this decision still does not grant on its own.

What that run was, exactly, so it can be repeated or disputed rather than taken on trust. Promethee 1.3.26, the build the `win-stable` channel index named at the time, `Promethee-1.3.26-full.nupkg`, SHA-1 `DC7A47901AFBAA8CB56A4A73D3982CF7C2834C82`, 426760554 bytes. It ran under the Linux wrapper at commit `4c377553458553903836358cb07e7fbd3edf15fe` of `Akayashuu/promethee-linux`, which redistributes none of that package and fetches it from Promethee's own channel at build time. The session was Hyprland on Wayland. Nothing about the run was reconstructed from memory: the hash and the byte count are the channel's own index entry, and the version is what the unpacked application reports for itself.

The helper on the acting side is worth naming with the same precision, because two of its numbers decide whether an action can leave the user's session in a state they did not ask for. A press is bounded at 1.2 s of conversation with the compositor, plus a grace of 0.25 s for the release and another for letting go of the display; the release is owed from the moment the press is written rather than from the moment it is acknowledged, so a timed-out press still puts the button back up. Electron waits 2.5 s for that, on Linux only, which is above everything the helper can spend. macOS and Windows keep the 800 ms they had. The alternative was leaving the caller free to kill a helper mid-press, and what that leaves behind is a mouse button held down over somebody else's window.

The read is bounded the same way, at 0.9 s, and Linux waits 1.5 s for it. The reason it needed a deadline at all is worth stating, because it is not the one the press had. The press makes a fixed number of round trips and the old bound was merely too small for their sum. The read waits in three loops that end when the compositor sends one particular event, and a socket timeout does not end those: a compositor that keeps answering something else keeps every round trip succeeding and holds the loop open for as long as it likes. One of those loops also runs once per candidate window. So the bound there is not a larger number replacing a smaller one, it is a bound where there was none.

Placement receipts are read the same way round. A compositor's acknowledgement is counted against the commands sent and every part of it has to be a success token, rather than the reply being scanned for the word `error`. Hyprland answers a spelling it does not carry with `unknown request`, which names no error, so the older reading called a batch that did nothing a placement. Sway splits a payload on commas as well as semicolons and answers once per part, measured on 1.12 rather than assumed. Anything short of the exact count is `attach-incomplete`, which retries and then takes the surfaces down, so the failure shows as an absent window rather than as one parked in the wrong place.

## Rationale

The three-slot probe is not a preference among mechanisms, it is what the platform forces. No single mechanism covers the sessions the helper already discovers windows on, so a decision to pick one is a decision to drop the others, and every candidate drops something real: portals-only drops Hyprland, Sway and X11 and would leave this work untestable on the machine it is written on; wlroots-only drops GNOME and KDE, which is most desktop Linux; X11-only drops the direction the platform is moving in.

Ordering wlroots first rather than the sanctioned portal is the one choice that looks backwards and is not. The portal is the better contract where it exists, but on the wlroots compositors it either does not implement the interface at all or wraps the same protocols behind a prompt, so asking it first would trade a working path for a worse one on exactly the sessions with evidence.

Refusing to fall through costs coverage and buys the only property that matters here: a click always goes to the session the geometry was read from.

Requiring in-app consent on top of a passing probe is redundant on the portal slot and is the entire consent story on the wlroots slot. Making it uniform means the user's answer means the same thing on every session, which a probe result does not.

Blocking on the classifier before the transports is deliberate sequencing. The transports are the interesting work and the classifier is the part that decides whether any of it ever runs.

## Consequences

### Positive

- Linux gets the same two actions as macOS, through the same preflight, with no new action authority and no new setting.
- The three slots cover Hyprland, Sway, river, Wayfire, GNOME, KDE and X11 between them, which is the widest reach available without inventing a protocol.
- Capture and injection answer separately, so a session that can do one and not the other says so instead of failing whole. i3 is exactly that session, and it gets the reading half rather than nothing.
- Sway gets both halves, on the same evidence standard Hyprland was held to, and the capture slot now takes three shm formats instead of one, so a compositor's choice of renderer no longer decides whether the HUD can be read.
- X11 gets both halves too, on that same standard, which covers every session that still runs an X server as its own window server and is the half of the platform the Wayland slots reach none of.
- The X11 capture reads the window's own Composite pixmap rather than the root, so the guarantee that nothing behind the HUD reaches the classifier holds on both built slots rather than on one, and it holds even when another window is covering the HUD entirely.
- The capture slot hands over the HUD's own surface rather than the screen under it, which is a stronger guarantee than macOS gets from `screencapture`. Nothing the user has on screen behind the HUD can reach the classifier, or this process, at any point.
- The wire format, the kill switch, and the two independent settings are unchanged, so nothing downstream of `permission-status` has to learn about Linux.

### Negative

- Six implementations behind two probes, two of which have no evidence at all, against protocols that are not versioned contracts.
- Capture slot 1 is built on a staging protocol. Staging is the sanctioned track and it is still a track: the interface can change name or version before it stabilizes, and a compositor may ship a version this helper does not bind. The alternative was a single compositor's own protocol, which trades that risk for a narrower one.
- The portal slot brings DBus and PipeWire into the native helper, which is the largest dependency this project has taken on, and it is required for the two desktops most users run. GNOME and KDE both need it on both halves, so until it is built neither desktop gets capture or injection, and that is most of the Linux install base.
- The same feature asks for consent differently depending on the session: a system prompt on portals, nothing at all on wlroots. That is a real inconsistency in the product and it is described rather than hidden.
- On the wlroots slot the user has no system-level revocation, so uninstalling or the in-app setting is the only way back.
- The cursor is left on the control the automation pressed, because Wayland offers no way to read where it was. A user typing with the pointer parked somewhere useful gets it moved out from under them once a Pomodoro phase ends, and there is no fix for that on this slot, only disclosure.
- The helper now links libwayland and generates five protocol bindings at build time, all of them vendored into the repository because they live in different packages on every distribution and one of them is not packaged at all on some. That is a build dependency and five copied files where before there was neither.
- The captured raster reaches the app through a file in the system temporary directory rather than through the pipe every other receipt uses, because a raster on the receipt channel would be the one answer a caller has to read differently. The file is written, read and removed inside one call, and it is still a window of a few milliseconds in which the HUD's pixels exist on disk.
- i3 users get observation, capture and no automation, for a reason that is about missing evidence rather than about their window manager. The X11 slot they would use now exists and works, so what stands between them and automation is that no i3 session has run it, which is a smaller gap than before and still a gap.
- The X11 capture has a path where it redirects a window that nobody had redirected, and that path can return a frame the client has not finished repainting. It is the path a bare X server with no compositing manager takes, which is also the session where the HUD would not be translucent in the first place, so it is the least likely and the least trustworthy at once.
- The pointer is left parked on X11 as well, even though X11 alone among the three could read it back and restore it. That is a deliberate uniformity rather than a limit, and it means one platform behaves worse than it has to so that one sentence of consent copy stays true everywhere.
- The helper now links libXcomposite and libXtst on top of libX11, so the Linux build asks for two more development packages than it did, and CI installs them.
- The capture path now carries three pixel packings instead of one, so a bug in the repacking would be a wrong raster rather than a refusal, which is the harder failure to notice. It is held down by a fill this project computes rather than by comparing one capture against another.
- Permission stops being a two-state answer. Every platform used to be either granted or denied, and Linux adds a third, a session with nothing to ask, which travels outside the frozen wire format as its own receipt. The format is unchanged, but the reading of it is now platform-dependent, and the same unreadable answer means denied on macOS and unavailable on Linux.

### Neutral

- Linux stays out of the release under ADR-0020 whatever this decision's status becomes.
- An official Promethee bridge remains the preferred migration target and would retire all six implementations at once.
- The classifier change is not Linux-specific work; deriving control centres from measured discs is how it should have read every platform.

## Validation

- The slot probes are exercised with injected transports so that order, first-binding-wins, and the refusal to fall through are provable without a live session.
- `permission-status` is exercised for each combination of capture and injection availability, including capture without injection and the reverse, and for the i3 refusal.
- A session with no mechanism at all, an unreadable receipt, and a helper that will not run are each exercised and each leave Linux unavailable rather than denied, against the same three cases on macOS, which stay denied. This is the assertion that keeps the recovery UI off a session that has nothing to recover.
- CI asserts the Linux `self-test` and `permission-status` receipts and their exit codes on a runner with no compositor, so the path that decides whether Linux automation exists at all cannot rot unnoticed between live sessions. It asserts the `capture` refusal there too, and that the refusal left no file behind: a runner that never showed a HUD is the one session where a written raster would be provably wrong.
- The Electron capture module is exercised against a stand-in helper that writes real bytes to the path it was handed, so a module that reports success without reading the file cannot pass. A receipt naming a different geometry or a different generation is refused rather than classified, because pixels separated from their receipt carry no evidence of which HUD they came from.
- The captured file is asserted to be gone after the call that asked for it, on the refusal paths as well as the successful one.
- The accepted capture formats are checked against what they should produce rather than against each other. Where a session offers two of them, the same live HUD is captured in both and the colour channels are compared byte for byte. Where a session offers only one, the target is a client whose fill this project computes, so a swapped channel fails where comparing two captures of the same surface would not.
- Consent tests prove that a passing probe alone never arms an action, that the two settings stay independent, and that the kill switch overrides both.
- The consent copy is exercised against the model rather than against the platform name, in both languages: every sentence that sends a macOS user to a system pane has a counterpart for the session that has none, and a test fails if a session sentence names one anyway.
- The classifier is exercised against measured Linux rasters in both states, and against fixtures whose discs sit on a half pixel rather than on the offsets the classifier samples, so that a wrong offset can fail a test.
- One fixture draws the Play triangle at the width the Linux HUD draws it rather than the width the other fixtures draw it, transcribed row by row from the capture, so a glyph test that only works at one size can fail a test.
- The capture slot is exercised on a live session against a HUD that has another window behind it, and the resulting raster is asserted to carry none of it, because the flatness gates cannot tell a contaminated raster from a valid one on thresholds alone and so cannot be the thing that catches this.
- The X11 capture is exercised against the read it refuses to be, and not only against itself. An opaque window is raised over the target so that a root grab of the same rectangle returns that window's colour and nothing of the HUD, and the capture taken at that moment is asserted byte-identical to one taken with nothing covering it.
- Both X11 capture paths are exercised: one where a stand-in has already redirected every top-level window, as a compositing manager does, and one on a bare server where the helper redirects the window itself and unredirects it afterwards.
- The slot selection is exercised for a session that offers both window servers at once, so that a Wayland session is never read through its X server and an X11 session never through a compositor socket it does not have.
- No validation run sends an action to a live Promethee process. Each platform proof needs its own explicit authorization and records the exact Promethee, compositor, and session configuration. The Linux Pause and Resume of 2026-08-27 were each authorized on their own by the owner of the session, and the session was left in the state it was found in.

## Revisit triggers

- The project owner accepts or rejects this decision.
- A capture succeeds and a press is sent on a real i3 session, which is the whole of what the automation refusal there is now waiting on, since the slot it depends on exists and answers. The same trigger fired for Sway and has been discharged.
- The X11 slot runs under a real compositing manager rather than under a stand-in that redirects and draws nothing, and against a real Promethee rather than a synthetic client. Those are the two things its evidence lacks.
- Whether Promethee's HUD answers a pointer drag at all is established independently, on a session nobody else is using, which is the one thing that would turn the drag leg of the pointer test from an attempt into a probe.
- Promethee publishes a Linux build, at which point every measurement here should be repeated against it rather than against its Windows release run on a Linux Electron.
- The consent copy stops being selected per platform and starts being selected per slot, at which point the X11 slot restoring the pointer becomes possible to state truthfully and should be reconsidered.
- A compositor offers the toplevel in a packing none of the three accepted formats describes, at which point `capture-format-unsupported` names it and the list is weighed again rather than grown by reflex.
- A live Sway session runs the flow against a real Promethee rather than against a synthetic client, which is the one thing the Sway evidence still lacks: the press and the capture are proven, the classifier has never read a Sway-rendered HUD.
- The Hyprland portal implements RemoteDesktop, which would collapse slot 1 and slot 2 into one path for that compositor.
- Wayland gains a sanctioned protocol for moving the pointer that all compositors implement, which would retire the injection probe. The capture probe is most of the way there already: `ext-image-copy-capture-v1` stabilizing, or Mutter implementing it, would collapse the capture table to one row.
- `ext-image-copy-capture-v1` changes shape before it stabilizes, or a compositor ships a version the vendored description does not describe, which is the cost of building on the staging track.
- A wlroots compositor makes the virtual-pointer protocol privileged or promptable, which would change what consent means on that slot.
- Promethee publishes an official session-control bridge, which would remove the need for capture and injection entirely.
- A reviewed Promethee version changes the HUD layout or glyphs, which the disc measurement above would no longer describe.
