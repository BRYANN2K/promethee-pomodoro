# Architecture decision register

This register records durable architecture decisions for Promethee Pomodoro. An accepted decision governs new work even when only part of the Electron target is verified. Implementation status is established by source/tests and explicit platform/release evidence, not by ADR status alone.

## Status vocabulary

- **Proposed** — under review and not yet binding.
- **Accepted** — approved by the project owner and governing new work.
- **Deprecated** — retained as history but no longer recommended.
- **Superseded** — replaced by a named later decision.

## Decision relationships

- ADR-0001 establishes the host platform for ADR-0002 through ADR-0007.
- ADR-0002 defines the adapter used by ADR-0004 and the compatibility boundary strengthened by ADR-0006.
- ADR-0003 owns Pomodoro time and phase state; ADR-0004 coordinates that state with Promethee session state.
- ADR-0005 consumes HUD geometry and state exposed under ADR-0002 and guarded by ADR-0006.
- ADR-0017 supersedes ADR-0015's primary-channel selection and activates/narrows ADR-0008: V1 is the public unscoped `promethee-pomodoro` npm package, with `1.0.1` as the first published version after the preserved failed `v1.0.0` candidate, while the macOS source installer and manual GitHub Release check remain secondary. Stable publication used exact manual approval plus verified workflow/registry readback. All three decisions defer, but do not supersede, the native signed distribution proposed by ADR-0007.
- ADR-0010 supersedes the unaccepted ADR-0009 proposal and amends ADR-0005: the outline remains fully input-transparent; Promethee-owned Tasks and transient surfaces stay immobile and retain z-order/input precedence; local handle/menu/tooltip windows may appear only from a complete revision-coherent exclusion set in a safe rectangle, otherwise they remain queued and hidden. Host exclusion schemas, pre-interactive publication, and platform precedence still require Promethee-owner approval and upstream source mapping.
- ADR-0014 composes ADR-0011, ADR-0012, and ADR-0013 as the accepted external bridge. It replaces only ADR-0002's upstream-owned transport requirement for this companion, preserves the typed adapter/session authority, and amends ADR-0006 with explicit compatibility, freshness, and non-authoritative outcomes.
- ADR-0016 amends ADR-0011's active execution mechanism: Electron uses the native helper and rendered Pause/Play evidence with CoreGraphics on macOS rather than AppleScript/JXA or semantic AX actions. The current Windows V1 helper is observation-only and exposes no input action. New installs default automatic Pause on and automatic Resume off; stored preferences remain unchanged and the kill switch overrides both. The one authorized macOS 1.3.29 same-session flow is narrow live evidence; Windows runtime remains unproven.
- ADR-0012 amends only ADR-0002/ADR-0006's task-read and blanket SQLite prohibitions: the main-process provider may read only `tasks` and `task_projects` under a strict read-only, fixed-query contract. The macOS product entry point wires that provider to its local picker; this grants no session, mutation, credential, private IPC, or arbitrary database authority.
- ADR-0013 accepts the minimal session observer after sanitized 1.3.29 research. It remains non-authoritative and cannot acknowledge/correlate a command or authorize retry.
- ADR-0007 must preserve the platform, compatibility, and security boundaries established by ADR-0001, ADR-0002, and ADR-0006 when native packaging resumes.
- ADR-0018 completes ADR-0001's migration boundary: Electron/TypeScript/npm is the only retained implementation; Swift/prototype/design-preview artifacts are no longer a recovery path. Historical ADR rationale remains, without links to deleted files.
- ADR-0020 extends ADR-0016's observation-only helper boundary to Linux x64 and adds a fourth candidate target to ADR-0017. It added no action, permission, or setting authority: `supportsNativeAutomation` stayed false there, so ADR-0011 and ADR-0016 Pause/Resume authority did not reach Linux until ADR-0021 lifted that one clause. Window discovery moves to the session's own window server because a Wayland client cannot enumerate another client's windows; live evidence covers one Hyprland session, where attachment to the real HUD was observed, plus a synthetic X11 exercise.
- ADR-0021 proposes lifting ADR-0020's no-action clause and nothing else in it. It extends ADR-0011 and ADR-0016 authority to Linux without widening it: the same two actions behind the same preflight, receipt, and no-retry rule. Because no Linux mechanism covers every session, capture and injection each become a three-slot probe, sanctioned or wlroots protocol first, then XDG portals, then X11, with the same refusal to fall through that ADR-0020 set for discovery. Only the first slot of each has live evidence, and only on Hyprland. Automation stays unavailable on i3 for want of any evidence, though capture is offered there because reading is not acting. The middle slot is now out of scope by decision: KDE and GNOME are not targets of this work, so slots 1 and 3 are what gets built and the portal slot stays a proposal with no code. The classifier gate that blocked the whole path is closed: a real Linux HUD is now classified in both states, after two corrections of the same kind, a control centre and a glyph shape each read from the raster instead of from a constant calibrated on one rendering. Both first slots are now built into the shipped helper, whose `self-test` answers `pause-resume` where ADR-0020 recorded `observe-only`, and whose `permission-status` gains a third answer, `automation-unsupported`, for a session with no mechanism to ask, which the app reads as unavailable rather than denied. Capture turned out not to need the compositor-specific protocol the first draft feared: `ext-image-copy-capture-v1` sourced from an `ext-foreign-toplevel-list-v1` handle returns the translucent HUD's own surface rather than a region of the screen, which is the raster the classifier was written for. Its reach was then measured rather than inferred, in four nested sessions, and it is narrower than this record first claimed. KWin 6.6.5 and Mutter 50.4 advertise none of the protocols either half binds, so KDE moves from capture slot 1 to the portal slot it was already assigned for injection and the two desktops most users run need a slot that does not exist yet; Mutter offers no window listing either, so GNOME loses the attached surface as well. Sway 1.12 advertises all of them, and the refusal to automate there, which was this project's decision rather than a limit of that session, is now lifted on the evidence it said it wanted: `permissions,1,1`, a `captured,159,32,0` checked against a computed fill, and Pause and Resume presses the target confirmed arriving on its own surface. Getting there required admitting that asking for ARGB8888 by name was a reach limit and not a safeguard, since the offered format comes from the renderer and the same Sway offers XRGB8888 under pixman; capture takes ARGB8888, XRGB8888 and BGR888 now, and the same live HUD read through the first two differs in none of its colour bytes. The format refusal also exposed a receipt that lied: a surface found and declined for its format answered `timer-not-found`. The helper gains `capture-format-unsupported` for it, read as unavailable rather than as a wrong request. Slot 3 is then built as well, and it does not read the screen: capture goes through `XCompositeNameWindowPixmap` and `XGetImage` on the window's own off-screen pixmap, injection through XTest, and the slot is chosen by whichever window server answered `windows` rather than independently, so a Wayland session that also runs an X server is never read through the wrong one. A nested Xorg 21.1.24 answers `permissions,1,1` there and returns a raster that matches a fill this project computes, on a server with a compositing manager and on a bare one where the helper redirects the window itself. That it is the window and not the screen was falsified rather than assumed: an opaque window raised over the HUD turns a root grab of the same rectangle entirely that colour while the helper's capture stays byte-identical to the uncovered one. i3 keeps the automation refusal, but the ground has narrowed to the one that is left: the slot it would use now exists and works, and what is missing is only that no i3 session has run it. The in-app consent gate now says what it is asking for: where no system prompt exists, the panel drops the settings buttons that would lead nowhere and states that the switches are the whole of the permission and that the pointer stays where the automation left it. On 2026-08-27 the path was closed end to end on one authorized live session: Pause, the paused surface captured and read as `paused`, then Resume, with the HUD geometry changing both ways and returning to where it started. The receipt stays `sent-unconfirmed`, so that geometry change is this project's observation and not an acknowledgement from Promethee.
- ADR-0019 uses ADR-0012 task/project observations and ADR-0013 running state to build a separate local reporting ledger. It narrows ADR-0013 only by allowing locally derived interval timestamps and selected task/project snapshots; Promethee session identifiers remain ephemeral, and no write, acknowledgement, causation, or retry authority is added.

## Maintenance

Do not rewrite an accepted ADR to make history match a later choice. Add a new ADR that supersedes or amends it, update this index, and link both records. Revisit an ADR when one of its explicit triggers occurs.
